# 位置 06「推演·发现关系」重审重做

## 1. 重审结论

原任务“根据三条规则完成外框配对”不宜继续使用。它把`丙=圆框`、`甲≠方框`和“各用一次”直接写成规则，学生主要做的是保留条件、排除选项并推出唯一结论，更接近“推演·推出结论”，不能清楚证明学生是否善于从多次观察中发现稳定对应。

新版改测：**面对几次同时出现的记录，能否找出对象之间固定的对应关系。**题面只交代装置怎样工作，不给任何具体对应规则；关系必须由三次记录共同恢复。

## 2. 三个候选方案比较

| 方案 | 核心材料 | 学生要做什么 | 优点 | 主要风险 | 裁决 |
|---|---|---|---|---|---|
| A. 按钮与灯 | 两个按钮同时按下，显示同时亮起的两盏灯；共三次记录 | 恢复每个按钮固定控制哪盏灯 | 场景一眼能懂；对应关系清楚；无学科知识；可精确枚举 | 若按钮行和灯列同序，答案会形成对角线 | **采用**；灯选项顺序按会话种子排列 |
| B. 卡片与印记 | 每次抽出两张卡，桌面同时出现两个印记；共三次记录 | 恢复每张卡带来哪个印记 | 同样能测交叉记录中的对应 | “印记从哪里来”不如按钮点灯直观，需多一句解释 | 仅作内容替补 |
| C. 三个盒子与声音 | 每次同时打开两个盒子，播放两种声音；共三次记录 | 恢复每个盒子对应哪种声音 | 可减少文字 | 手机静音、环境噪声、听觉差异和资源加载会引入额外误差 | 不进入 V1 |

最终只推荐方案 A。方案 B 与 A 的底层关系等价，但没有更高的理解收益；方案 C 会把听觉条件带入测量。

## 3. 最终入选任务：三次点灯记录

### 3.1 基本登记

- 位置：`06`
- 一级能力：`推演`
- 二级机制：`发现关系`
- `itemId`：`IN-RL-01R2`
- `itemVersion`：`infer-relation-cooccurrence-lights-v0.4`
- `answerRuleVersion`：`infer-relation-cooccurrence-lights-answer-v0.2`
- `taskRole`：`direct`
- 目标难度：容易—中等（待校准）
- 预计有效作答时间：35 秒；合理观察区间暂记 18—70 秒，正式界限须由上线数据校准
- 练习：无；交互只需逐行点选，首屏用一句微提示说明操作

### 3.2 学生端文案

顶部短提示：

> **从三次记录里，找出按钮和灯的固定对应。**

装置说明：

> 每个按钮都固定控制一盏灯。下面记录了每次同时按下两个按钮后，亮起的两盏灯。

题干：

> **请找出：甲、乙、丙各控制哪盏灯。**

操作提示：

> 每行选择一盏灯，选完后提交。

学生端不出现“构念、双射、共现、交集、映射、推演、枚举”等术语，也不显示即时对错。

### 3.3 正式材料

三张记录卡持续显示，标准内容为：

| 记录 | 同时按下 | 同时亮起 |
|---|---|---|
| 记录 1 | 甲按钮 ＋ 乙按钮 | 三角灯 ＋ 圆灯 |
| 记录 2 | 甲按钮 ＋ 丙按钮 | 圆灯 ＋ 方灯 |
| 记录 3 | 乙按钮 ＋ 丙按钮 | 方灯 ＋ 三角灯 |

上表的灯顺序已刻意反对齐；三次记录所表达的集合内容仍分别是`{甲,乙}→{圆,三角}`、`{甲,丙}→{圆,方}`、`{乙,丙}→{三角,方}`。灯的书写先后不代表按钮与灯逐个相连。

视觉制作要求：

- “按钮”统一画成同尺寸圆角按键，按键内显示甲、乙、丙；同一按钮在三张卡中外观完全一致。
- “灯”分别使用圆、三角、方三种大轮廓，并在轮廓下同时写“圆灯、三角灯、方灯”；不能只靠颜色区分。
- 亮起状态统一使用同一种浅金填充和外发光，不为不同灯使用不同颜色。
- 每张卡使用上下两个无连线的集合区块：上方“同时按下”放两个按钮筹码，下方“同时亮起”放两个灯图标；不使用左右两列或上下两行逐项对齐的表格。
- 三张记录卡的按钮区和灯区尺寸完全一致；不通过距离、大小、线条粗细暗示配对。
- 每张记录明确表达“这次恰好显示这两个按钮和这两盏灯”，不画第三个未按按钮或未亮灯，避免学生误把空间位置当一一连线。
- 记录卡显示顺序由`presentationSeed`在 6 种排列中确定。V1 卡内采用上表固定的反对齐顺序；若后续按种子改变卡内顺序，生成器必须通过位置泄漏校验：按同位强行配对时，同一按钮在不同记录中会得到冲突结果，并且不能直接还原标准答案。不合格的展示种子必须重抽。

### 3.4 作答区与交互

记录卡下方按固定顺序显示三行：

| 按钮 | 可选灯 |
|---|---|
| 甲控制 | 圆灯 / 三角灯 / 方灯 |
| 乙控制 | 圆灯 / 三角灯 / 方灯 |
| 丙控制 | 圆灯 / 三角灯 / 方灯 |

- 三行共用同一个`lightOptionOrder`；灯选项顺序按`presentationSeed`在 6 种排列中确定，并在整题内保持不变。
- 每行是单选；允许随时修改或清空。
- 编辑过程中不自动禁用别行已选的灯，不提示“重复”，不高亮相关记录，也不显示完成度以外的线索。
- 三行均已选择后才启用“提交”；提交后锁定，不回显正确答案。
- 不使用拖拽；整张选项按钮可点，图形与文字都是同一点击目标。
- 记录卡始终可见；学生不需要记住前一张记录。

### 3.5 正确答案与评分

标准答案：

- 甲 → 圆灯
- 乙 → 三角灯
- 丙 → 方灯

原始观察点：

- `p1_jia_circle`：甲选择圆灯，1 分；否则 0 分。
- `p2_yi_triangle`：乙选择三角灯，1 分；否则 0 分。
- `p3_bing_square`：丙选择方灯，1 分；否则 0 分。
- `exact_mapping`：三项全部正确时为`true`。

服务端保存`rawPointVector: [p1_jia_circle, p2_yi_triangle, p3_bing_square]`。三个点共享同一材料，不应在信效度分析中假装成三个独立题；节点级`exact_mapping`是主要计分证据，分项只用于观察错误落点。一级/二级机制合成时，位置 06 的最大贡献始终是**一个任务节点**，不能因三个分项而获得三倍证据权重；它只与位置 29 构成两个独立任务来源。V1 不在学生端显示本题得分、速度等级或能力高低。

### 3.6 唯一答案枚举核验

令每个按钮固定对应圆`O`、三角`T`、方`S`中的一个灯。三次记录要求：

- `{f(甲), f(乙)} = {O, T}`
- `{f(甲), f(丙)} = {O, S}`
- `{f(乙), f(丙)} = {T, S}`

对三个按钮分别取三种灯的全部`3³ = 27`种固定对应进行枚举，只有一组同时满足三条记录：

`f(甲)=O，f(乙)=T，f(丙)=S`。

因此唯一性不依赖额外写出“三盏灯各用一次”。即使学生只读到“每个按钮固定控制一盏灯”，三次记录也足以确定唯一答案。开发端必须以三条集合相等谓词核验答案，不得只硬编码某个点击路径。

建议自动化测试至少覆盖：

1. 27 组映射中恰好 1 组通过答案谓词；
2. 三张记录的 6 种显示顺序不改变唯一答案；
3. 灯选项 6 种显示顺序不改变评分；
4. 三行任一项错误时`exact_mapping=false`；
5. 暂时重复选择不会触发提示或自动改动别行答案；
6. 页面实际渲染的按钮/灯数组顺序不会被答案谓词当作对应关系；
7. 每个允许的卡内顺序变体都通过反对齐校验，按同位匹配不能直接得到正确答案。

## 4. 为什么主要测“发现关系”

### 4.1 目标证据链

学生需要把三次记录放在一起比较：甲同时出现在记录 1 和记录 2，而两次亮灯中共同出现的是圆灯，因此可以发现甲与圆灯稳定对应；再用其余记录恢复乙和丙。有效信息不是一道显式条件，而是**多次观察中反复一起出现的对象**。

题目要求学生重建“谁和谁固定对应”，没有让学生判断某句话是否必然成立，也没有把具体对应以`等于/不等于`规则直接给出。因此，它比原外框题更贴近“发现关系”，与“推出结论”形成可解释边界。

### 4.2 仍然存在但可接受的辅助过程

- 学生可能先发现甲—圆，再用排除完成其余两项；排除是完成任务的辅助步骤，不是题面预设的主要规则形式。
- 学生也可能直接比较记录 1 与记录 3，先找到乙—三角；不同起点都在利用跨记录的稳定对应。
- 题目不可证明学生使用了哪条心理路径，因此报告只能把它作为“发现关系”的一份任务证据，并与位置 29 的新场景关系任务共同解释，不能仅凭位置 06 给学生定性。

### 4.3 相邻机制排除

| 可能混入的能力 | 控制方式 |
|---|---|
| 推演·推出结论 | 不提供`甲≠方`等显式条件，不要求判断结论真伪；答案对象就是稳定对应本身 |
| 推演·找到规律 | 没有时间序列、重复变换或“下一项”，不靠猜变化套路 |
| 数理·数量关系 | 数字只用于记录编号；没有计算、比例、倍数或数量结构 |
| 语言·理清关系 | 全题使用短句和重复句式；理解装置后无需处理语义层级、转折或长文本 |
| 记忆 | 三次记录持续显示；不要求延迟保存材料 |
| 空间 | 图形仅作灯的标签；不要求旋转、组合、定位或补全 |

## 5. 干扰项与泄漏控制

- 错误映射不设计成完整方案四选一，避免靠“某项看起来更整齐”猜中。
- 不把标准答案排成固定对角线；记录顺序与灯选项顺序分别保存，评分按稳定 ID 而非屏幕位置。
- 图标旁保留文字，避免学生因不熟悉形状名称或低视力而受损。
- 不出现连接线、靠近关系或同色编码；这些都会直接泄漏对应。
- 构建时运行`positional_pairing_leak`检查；实际渲染若未通过反对齐校验，本节点标记 invalid，不进入能力合成。
- 选择后不重排选项、不隐藏重复选项、不播放与某盏灯相符的动画。
- 三张记录必须同时加载完成后才触发`item_shown`；任一图标资源缺失则阻止计时并标记`asset_incomplete`。
- 不以“很快完成”直接加分。速度只用于后续识别异常响应和群体校准。

## 6. 移动端与无障碍规格

- 以 360px 宽手机为基准：三张记录卡纵向排列，单卡建议高 84—96px；作答三行置于其下，允许一次自然纵向滚动，不做横向滚动。
- 每个灯选项点击区至少 48×48px；行标题宽度保证“甲控制”不换成单字竖排。
- 选中态同时使用 2px 深色描边、勾号和`已选择`可访问状态，不能只变色。
- 形状 SVG 使用清晰闭合轮廓；高对比模式下移除发光但保留粗线和文字。
- 每张记录的可访问名称示例：`记录一：同时按下甲按钮和乙按钮，圆灯和三角灯亮起。`
- 每个选项使用原生 radio 语义；三组分别命名为`甲控制的灯`、`乙控制的灯`、`丙控制的灯`。键盘可用方向键切换，读屏能读出组名、选项名、选中状态。
- DOM 与 alt 不包含“正确、对应、交集”等额外线索；无障碍文本只等价描述屏幕可见信息。
- 字号：题干 18—20px，材料和选项不低于 16px；支持系统字体放大到 200%，内容按纵向重排且不遮挡提交按钮。

## 7. 数据与事件字段

沿用总稿通用事件：`item_route_entered`、`asset_request_started`、`asset_decoded`、`item_shown`、`first_action`、`answer_changed`、`confirm_enabled`、`item_submitted`、`item_locked`、`visibility_hidden`、`visibility_visible`、`sync_queued`、`sync_succeeded`、`sync_failed`、`resume_restored`、`zoom_used`、`a11y_mode`。

本节点增加：

- `relation_record_set_shown`：字段`recordOrder`、`buttonPairOrderByRecord`、`lightPairOrderByRecord`。
- `mapping_cell_selected`：字段`buttonId`、`lightId`、`previousLightId`、`screenPosition`。
- `mapping_cleared`：字段`buttonId`、`previousLightId`。
- `mapping_completed`：三行首次均有选择时触发；只记录完成时点，不判断正确。

每个事件至少保存总稿规定字段：`sessionId`、`itemId`、`itemVersion`、`eventId`、`clientTs`、`serverReceivedTs`、`activeElapsedMs`、`presentationSeed`、`optionOrder`、`deviceClass`、`viewport`、`clientVersion`。本题`optionOrder`具体保存为`lightOptionOrder`。

客户端只提交作答与实际呈现顺序，不持有或生成正确答案字段：

```ts
type Position06ClientAnswer = {
  mapping: {
    jia: 'circle' | 'triangle' | 'square'
    yi: 'circle' | 'triangle' | 'square'
    bing: 'circle' | 'triangle' | 'square'
  }
  recordOrder: string[]
  buttonPairOrderByRecord: Record<string, string[]>
  lightPairOrderByRecord: Record<string, string[]>
  lightOptionOrder: Array<'circle' | 'triangle' | 'square'>
  revisionCount: number
}
```

服务端核验三条记录与映射后再生成评分字段：

```ts
type Position06ServerScore = {
  rawPointVector: [0 | 1, 0 | 1, 0 | 1]
  exactFlags: { exact_mapping: boolean }
}
```

正确答案、答案谓词和原始计分只由服务端持有；前端只提交稳定 ID 和显示顺序。提交与恢复遵守总稿的幂等、离线补传和去重规则。

## 8. 质量标记与上线前检查

建议质量标记：

- `rapid_random_response`
- `answer_pattern_risk`
- `interaction_error`
- `asset_incomplete`
- `viewport_risk`
- `positional_pairing_leak_risk`（素材/渲染审计标记，不是学生能力标签）

上线前必须逐项通过：

- [ ] 27 组固定对应枚举后只有标准答案通过。
- [ ] 记录 6 种顺序 × 灯选项 6 种顺序共 36 种组合均评分一致。
- [ ] 三张卡为集合式反对齐呈现；按同位强行配对时会产生冲突，不能得到正确映射。
- [ ] 客户端提交体不含`rawPointVector`、`exactFlags`或答案谓词；这些字段只由服务端生成。
- [ ] 机制合成把位置 06 计为一个任务节点，三个分项不作为三个独立任务加权。
- [ ] 学生端没有出现具体对应规则、等式、不等式或即时排除提示。
- [ ] 三张记录同时可见，且按钮与灯在不同记录中使用完全相同的视觉资产。
- [ ] 任意一种错误映射都不会被服务端误收为`exact_mapping=true`。
- [ ] 读屏文本与视觉材料信息等价，不泄漏答案。
- [ ] 位置 06 只与位置 29 合并为“发现关系”证据；单项分数不直接生成学生标签。

## 9. 最终裁决

用`IN-RL-01R2 / infer-relation-cooccurrence-lights-v0.4`替换位置 06 的“三符号外框配对”。新版的核心行为是从三次观察中恢复稳定对应，题面自然、答案唯一、开发可枚举验证，也更容易与“推出结论”的显式条件推导区分。v0.4 已加入集合式反对齐呈现、客户端/服务端评分职责拆分和节点级单一证据权重三项约束。
