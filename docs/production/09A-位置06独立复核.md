# 位置 06「推演·发现关系」独立复核

## 1. 复核结论

**结论：方向成立，但当前规格应在并入 30 题总稿前完成 3 项必改。**

新版“三次点灯记录”明显优于原来的“外框配对”：具体对应不再以等式、不等式和排除规则直接给出，学生必须把三次观察放在一起，恢复按钮与灯之间的稳定对应。它主要测“发现关系”的证据链可以成立，学生文案也达到高中生一遍读懂的程度。

当前最大问题不在题意，而在视觉呈现：规格里的标准顺序恰好让每张卡的第一个按钮对应第一盏灯、第二个按钮对应第二盏灯。若照表直接制作，学生可以逐卡按位置配对，无需比较三次记录。这会破坏新版最重要的测量意图。

裁决状态：`conditional_accept`。

---

## 2. 构念复核

### 2.1 为什么新版更接近“发现关系”

三次材料给出的是观察记录，而不是具体规则：

- 甲＋乙 → 圆灯＋三角灯
- 甲＋丙 → 圆灯＋方灯
- 乙＋丙 → 三角灯＋方灯

学生需要识别跨记录中共同出现的对象：甲在前两次都出现，圆灯也在前两次都出现，由此恢复甲—圆灯；同理恢复乙—三角灯和丙—方灯。目标答案本身就是一组稳定对应，不是对某个候选结论作真假判断。

与相邻机制的边界基本清楚：

- 不是“推出结论”：题面没有给`甲≠方`、`丙=圆`等显式条件，也不问“哪句话一定正确”。
- 不是“找到规律”：没有时间序列、下一项或重复变换。
- 不是“数量关系”：没有计算、比例或数量结构。
- 不是“语言关系”：文字负担短且句式重复。

需要保留的谨慎表述：学生找到第一个对应后，仍可能通过排除完成其余两项。因此，本题是“发现关系”的一份主要证据，不是纯过程诊断；只能与位置 29 共同解释，不能仅凭本题生成学生标签。原稿已经写明这一点，合理。

### 2.2 难度判断

`中等 / 35 秒`只能作为预校准目标，不应写成稳定事实。题面短、材料持续显示，熟练学生用一次交叉比较即可完成，真实难度可能落在“容易—中等”之间。建议总稿登记为：

- 目标难度：`容易—中等（待校准）`
- 预计有效作答时间：`30—40 秒`

不据此修改计分，速度也不直接加分。

## 3. 唯一答案复核

令甲、乙、丙分别固定控制圆`O`、三角`T`、方`S`中的一盏灯。答案谓词为：

- `{f(甲), f(乙)} = {O, T}`
- `{f(甲), f(丙)} = {O, S}`
- `{f(乙), f(丙)} = {T, S}`

在允许按钮重复控制同一种灯的情况下，搜索空间为`3³=27`。三条集合相等约束仍只有一个解：

`f(甲)=O，f(乙)=T，f(丙)=S`。

因此原稿关于唯一性的判断正确，并且无需再向学生补充“三盏灯各用一次”。这比依赖双射前提更稳妥。

建议保留原稿列出的 27 组枚举自动化测试，同时增加一条素材渲染测试：**页面上按钮和灯的数组顺序不得被答案谓词当作对应关系。**

## 4. 三项必改

### 必改 1｜消除卡内位置直接泄漏

原规格标准表与“卡内左右次序固定”组合后，三张卡均形成正确的同位配对：

- 甲、乙 → 圆、三角
- 甲、丙 → 圆、方
- 乙、丙 → 三角、方

学生可能直接采用“左边第一个控制右边第一个”的视觉策略。此时即使不看另外两张卡，也能得到完整答案。

推荐修改：

1. 每张卡把“按下的一组按钮”和“亮起的一组灯”画成两个**无连线的集合区块**，不要画成两行对齐表格。
2. 三张卡使用经过校验的固定反对齐顺序，例如：
   - 记录 1：按钮`甲、乙`；灯`三角、圆`
   - 记录 2：按钮`甲、丙`；灯`圆、方`
   - 记录 3：按钮`乙、丙`；灯`方、三角`
3. 若希望按种子改变卡内次序，不能对四个列表独立随便随机。生成后必须检查：按同位匹配时，同一按钮在不同记录中会得到冲突结果，且不能直接还原标准答案；不合格种子重抽。
4. 事件中的`buttonPairOrderByRecord`和`lightPairOrderByRecord`必须保存实际渲染顺序。

这是并入总稿前的最高优先级修改。

### 必改 2｜前端提交与服务端计分职责要一致

原稿一方面写“正确答案、答案谓词和原始计分由服务端持有”，另一方面又在`Position06Answer`中要求前端提交`rawPointVector`和`exactFlags`。两者冲突，也会让正确答案或计分逻辑进入前端包。

推荐拆成：

```ts
type Position06ClientAnswer = {
  mapping: {
    jia: 'circle' | 'triangle' | 'square'
    yi: 'circle' | 'triangle' | 'square'
    bing: 'circle' | 'triangle' | 'square'
  }
  recordOrder: string[]
  buttonPairOrderByRecord: Record<string, string[]>
  lightPairOrderByRecord: Record<string, string[]>
  lightOptionOrder: Array<'circle' | 'triangle' | 'square'>
  revisionCount: number
}
```

服务端收到后再生成：

```ts
type Position06ServerScore = {
  rawPointVector: [0 | 1, 0 | 1, 0 | 1]
  exactFlags: { exact_mapping: boolean }
}
```

学生端、接口响应和日志均不在提交前返回正确答案。

### 必改 3｜明确分项依赖，避免把 3 个点击当成 3 道题

原稿已经提醒三个评分点共享材料，但实施端还需把规则写死：

- 节点级`exact_mapping`是本题的主要正确性证据。
- 三个分项仅用于错误分析和后续题目参数研究。
- 不能把三个分项当作三个独立样本抬高“发现关系”的稳定性。
- 一级/二级机制合成时，本节点的最大贡献仍是一个任务节点；与位置 29 构成两个独立任务来源。

否则看似得到 3 个“微判断”，实质仍是一次共同推断，统计解释会过度自信。

## 5. 建议优化但不阻塞并入

### 5.1 作答区防模式猜测

灯选项顺序按会话种子改变是合理的。需确保三行共用同一顺序，避免每行变化造成额外搜索负担；评分只认稳定 ID，不认列号。原稿此处可保留。

### 5.2 视觉分组

移动端可把每张记录卡分成上下两块：

`同时按下`下放两个按钮筹码，`亮起`下放两个灯图标，中间用一个向下箭头。这样比左右两列更不容易暗示位置连线，也适合 360px 屏幕。

### 5.3 学生文案

现有文案自然、短、无学术术语，可以直接使用。若要再压缩，可合并成：

> 每个按钮都固定控制一盏灯。看三次记录，找出甲、乙、丙各控制哪盏灯。

无需增加“每盏灯只能对应一个按钮”或解释解题方法，避免把关键关系直接教给学生。

### 5.4 质量标记

建议在原有标记外增加内部素材审计标记：

- `positional_pairing_leak_risk`

它不是学生表现标签，而是构建或渲染验收失败时使本题失效的质量标记。若实际渲染版本未通过反对齐检查，本节点应标记 invalid，不进入能力合成。

## 6. 高中生理解性检查

从语言与操作看，本题符合高中生手机独立完成条件：

- 场景不需要学科背景，按钮点灯是直观因果装置。
- 题干没有形式逻辑术语，理解成本低于实际关系发现成本。
- 三张记录持续显示，不额外测记忆。
- 三行单选比拖拽更稳定，误触后可修改。
- 圆、三角、方同时用轮廓和文字标记，对色觉差异友好。

唯一需防的不是“看不懂”，而是视觉排布把答案变得过于直接。完成必改 1 后，题意与目标难度更匹配。

## 7. 并入总稿的最终裁决

建议保留：

- `itemId`：`IN-RL-01R2`
- `itemVersion`：`infer-relation-cooccurrence-lights-v0.3`
- 三次记录的集合内容
- 甲→圆、乙→三角、丙→方的唯一答案
- 三行单选且不自动排除
- 27 组枚举核验

并入前必须修改：

1. 三张卡改为集合式、反对齐呈现，杜绝逐卡位置配对；
2. 客户端只提交作答与呈现顺序，服务端生成分项和`exact_mapping`；
3. 机制合成明确按一个任务节点计证据，不把三个分项当独立题。

完成以上三点后，本题可判定为`accept`，并可替换原位置 06“外框配对”。
