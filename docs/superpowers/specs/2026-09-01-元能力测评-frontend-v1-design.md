# 元能力快速测评 V1.0 学生端前端设计

状态：待确认后实施  
版本：Frontend Design 1.0  
日期：2026-09-01  
主要终端：学生在手机浏览器中独立完成

---

## 1. 本次实施目标

把现有 25 道单选原型升级为一套可完整体验的学生端前端，承载已经确定的 30 个固定任务、两套记忆材料和五段式学生报告。

本轮实现覆盖：

- 姓名、手机号、年级、高考外语语种四项必填；
- 测评说明和作答准备；
- Deck A、Deck B 两次记忆材料呈现；
- 30 个固定任务节点及所需交互；
- 进度保存、刷新恢复和本地断网留存；
- 完成后的结果生成过渡；
- 一句话结论、雷达图和五个报告模块；
- 手机端、桌面端、键盘和基础无障碍适配；
- 自动化测试和逐屏视觉验收。

本轮不实现：

- 正式常模、百分位、排名和固定能力等级；
- 动态选题；
- 选科组合填写或基于选科改变题目；
- 教师端、后台运营端、登录系统和短信验证；
- 生产数据库及跨设备找回；
- 未经校准的正式能力判定算法。

前端中的结果用于展示完整产品体验和验证页面逻辑。正式发布时，题目版本、证据聚合、学科映射和报告文案应由后端版本化服务返回。

## 2. 学生完整流程

```text
首页与信息采集
  → 测评说明
  → Deck A 呈现
  → 位置 01—17
  → Deck B 呈现
  → 位置 18—30
  → 整理结果
  → 学生报告
```

### 2.1 首页与信息采集

首页保留“看见你更容易怎样学会”的核心表达，明确“约 15 分钟”，不写固定题数。

四项必填：

- 姓名；
- 手机号；
- 年级：高一、高二、高三、高复；
- 高考外语语种：英语、日语。

手机号限制为 11 位中国大陆手机号格式。错误信息贴近字段显示，不用弹窗。学生确认信息用途后才可开始。

### 2.2 测评说明

用三条短说明完成预期管理：

1. 题目不考高中知识点；
2. 遇到不会的可以凭第一判断作答；
3. 作答过程中不显示对错，也不需要追求速度。

### 2.3 记忆材料

Deck A 在正式任务开始前呈现，Deck B 在位置 18 前呈现。两次均使用相同页面结构但不同材料和说明。

- 以卡片网格显示 6 组陌生配对；
- 呈现期间不可跳过；
- 只显示克制的时间进度，不显示秒数倒计时；
- 到时后自动开放继续按钮；
- 页面离开或切后台时暂停有效呈现计时，避免材料未实际看满；
- 不允许返回重新查看。

### 2.4 任务作答

学生端只显示百分比进度和当前任务提示，不显示“第几题/共几题”，不显示一级能力或二级机制名称。

每个任务一屏完成：

- 短题干；
- 必要时一行辅助说明；
- 任务材料；
- 交互区；
- “确认并继续”按钮；
- “作答过程中不会显示对错”提示。

未完成题目要求时，确认按钮不可用。提交后不能返回修改，避免记忆题泄漏和前题反复练习。

### 2.5 结果过渡

完成后先出现 1—2 秒的整理状态，用“正在整理你在不同任务中的表现”替代“正在计算分数”。本地证据保存成功后进入报告。

## 3. 页面和组件结构

### 3.1 顶层页面状态

```ts
type Screen =
  | 'intake'
  | 'instructions'
  | 'memory-a'
  | 'tasks'
  | 'memory-b'
  | 'processing'
  | 'report'
```

顶层运行器只负责流程、恢复和持久化，不在页面组件内硬编码题目内容。

### 3.2 任务渲染器

`TaskRenderer` 根据任务的 `interaction.type` 选择交互组件。首版至少支持：

| 组件 | 用途 |
|---|---|
| `SingleChoiceTask` | 文字、数量、规律和条件类单选 |
| `MultiJudgmentTask` | 同一材料下的多个独立微判断 |
| `MatchingTask` | 配对、对应和关系发现 |
| `OrderingTask` | 信息排序、词块排序、步骤排列 |
| `WordBlockTask` | 有限词块组成准确表达 |
| `SpatialChoiceTask` | SVG 图形、结构、想象和转换选择 |
| `StateSequenceTask` | 连续状态或操作结果判断 |

所有组件遵守同一合同：接收任务定义和当前草稿，返回结构化作答；组件不自行判分，不显示答案。

### 3.3 共用组件

- `BrandHeader`：品牌和低干扰状态信息；
- `ProgressBar`：只显示完成百分比；
- `TaskFrame`：题干、材料、交互和底部操作的统一容器；
- `MemoryDeck`：两套记忆材料呈现；
- `ResumePrompt`：检测到未完成记录时选择继续或重新开始；
- `ProcessingView`：结果整理过渡；
- `ReportView`：学生报告；
- `RadarChart`：五维表现雷达图；
- `ErrorBoundary`：单个题目渲染异常时给出可恢复提示。

## 4. 任务数据合同

每个任务以结构化数据定义，内容和交互分离。核心字段如下：

```ts
interface AssessmentTask {
  id: string
  version: string
  position: number
  dimension: 'memory' | 'language' | 'numeracy' | 'spatial' | 'inference'
  mechanism: string
  role: 'direct' | 'cross-representation' | 'context-transfer'
  pairId?: string
  difficulty: 'easy' | 'medium' | 'challenge'
  prompt: string
  helper?: string
  stimulus: StimulusDefinition
  interaction: InteractionDefinition
  responseSchema: ResponseSchemaDefinition
  expectedSeconds: number
}
```

学生端任务载荷保留机制、交互和响应结构，但不包含正确答案、评分谓词、能力权重或优势阈值。机制字段只用于运行时记录与研发检查，学生界面不渲染。

### 4.1 证据记录

每次提交保存：

```ts
interface TaskEvidence {
  taskId: string
  taskVersion: string
  position: number
  response: unknown
  scorePoints: number
  maxPoints: number
  startedAt: string
  submittedAt: string
  activeDurationMs: number
  interactionEvents: InteractionEvent[]
  viewport: { width: number; height: number }
}
```

作答时间不直接加分，只作为校准和异常识别证据。事件只记录完成任务必要的信息，例如选择、取消、排序完成和提交；不采集键盘输入内容以外的无关行为。

### 4.2 位置 06 的实现约束

位置 06 使用 `IN-RL-01R2 / infer-relation-cooccurrence-lights-v0.4`，不再使用旧版显式排除条件题。

- 同屏呈现三次按钮组合与三次灯光结果；
- 三张记录使用上下集合区块和经过校验的反对齐顺序，不能形成按钮与灯的同位配对；
- 学生根据共现记录完成按钮与灯形的对应；
- 不在题干中给出“每个只对应一个”等可直接套用的推理规则；
- 交互为三个按钮分别选择对应灯形，全部完成后才能提交；
- 选择过程不提示局部对错；
- 正确映射必须有唯一解；
- 客户端只提交作答和实际呈现顺序，分项与节点正确性由评分适配器返回；
- 三个映射分项共享一次推断，机制聚合时只计一个任务节点证据；
- 主要证据是从多次共同出现中抽出稳定对应，而不是沿条件链推出结论。

最终文字、图形参数和答案以位置 06 专项重审稿及独立复核结论为准。

### 4.3 位置 08 的实现约束

位置 08 使用 `SP-IM-08-NEW-01 / spatial-imagine-two-piece-outline-v0.1-precal.2`，不再使用可预览的缺口试配。

- 同屏给出两块抽象部件和各自标记的连接边；
- 题干要求沿标记边直接拼合，部件方向保持不变；
- 学生不能拖动部件、试拼或查看半透明预览；
- 四个候选整体的局部接口均看似可接，区别来自拼合后的整体轮廓；
- 不靠旋转、镜像和微小细节制造难度；
- 选项采用精确 SVG，正确答案必须通过几何核验保持唯一；
- 来源图使用一个冻结坐标系的 SVG；答案轮廓由权威单位格集合生成，并用统一留白 `viewBox` 防止描边裁切；
- 与位置 28 的遮挡、叠合或其他组合任务保持不同心理操作。

最终图形坐标和答案以位置 08 专项重审稿及独立复核结论为准。

## 5. 状态保存与恢复

首版使用版本化 `localStorage` 保存会话，数据键包含测评版本。每次提交后立即写入：

- 学生信息；
- 当前流程位置；
- 已提交证据；
- Deck A/B 是否完成规定呈现；
- 会话创建和最后更新时间。

刷新后：

- 已完成信息采集但未开始时回到说明页；
- 正在某题作答时回到该题，未提交草稿可恢复；
- 已提交的题不可再次打开；
- 已完成测评直接进入报告；
- 数据版本不兼容时提示重新开始，不静默混用旧题数据。

“重新开始”需要二次确认，只清除当前测评会话，不影响其他浏览器数据。

## 6. 报告结构

报告开头先给一句话结论，再显示五维雷达图。结论写优势能力，不输出“单入口、双入口、还需观察”等类型。

### 01｜我的元能力画像

- 一句话结论；
- 五维雷达图；
- 主要优势能力和可能配合的第二优势；
- 使用“在这次任务中”等限定表达。

### 02｜为什么这样判断

按记忆、语言、数理、空间、推演顺序展示五个维度。每个维度内部按既定顺序解释三个二级机制，并连接到相应任务证据。

不显示原始分、百分位、排名和能力等级。用“表现较稳定”“出现了优势迹象”“目前证据较少”等证据语言。

### 03｜我的学习优势

把能力表现翻译成学生能观察到的学习行为，例如更快抓住关系、容易把变化看成结构、能把表达组织清楚。避免人格化标签和万能鼓励。

### 04｜我的学科优势地图

先回答“哪些学科更容易发挥”，再回答“具体在哪些任务里发挥”。

- 后台保留语文、数学、英语、日语、物理、化学、生物、历史、政治、地理、技术 11 科；
- 根据学生填写的外语语种，只显示英语或日语，因此学生看到 10 科；
- 学科排序依据五维证据与学科能力底图的组合，但不能写成确定的学科适合性；
- 每科说明 2—3 个来自知识图谱的具体任务，例如审题关系、函数变化、实验推断、材料组织、地图结构等；
- 学科底图不能当作学生分数，也不能只用一级能力最高项粗暴匹配。

### 05｜我的优势学法

围绕“学、背、练、补”四种场景给具体方法：

- 学：新知识怎样进入；
- 背：怎样编码和提取；
- 练：怎样拆题、记录和复盘；
- 补：卡住时先改哪一种信息呈现方式。

每条建议采用教练式表达：看到的表现 → 可能的含义 → 可以怎样做。报告必须有学习建议，但不做 7 天计划和打卡任务。

## 7. 视觉与交互设计

视觉完全沿用此前已确认的“解码学习”测评风格，以下截图是实施基准：

- `design/assessment-concept.png`
- `design/report-concept.png`
- `design/qa-intro-mobile.png`
- `design/qa-question-mobile.png`

### 7.1 设计语言

- 背景：轻微冷白或纸张灰；
- 主色：深海军蓝；
- 强调：克制的金色；
- 少量状态提示：暗红；
- 标题：中文衬线体；
- 正文和交互：清晰无衬线体；
- 版式：大量留白、细分隔线、弱阴影、不过度卡片化；
- 图形题：使用清晰的内联 SVG，线宽和点击区适配手机；
- 不使用金币、排行、奖章、强游戏化或花哨动效。

### 7.2 响应式规则

- 以 390px 左右手机宽度为主设计；
- 触控目标不小于 44×44px；
- 底部确认按钮在短屏上可保持可见，但不能遮挡选项；
- 桌面端最大内容宽度限制在舒适阅读范围，不把手机布局无限拉宽；
- 空间图不依赖颜色区分答案；
- 支持系统减少动态效果设置。

### 7.3 无障碍

- 所有表单有可见标签和明确错误说明；
- 选项、排序和匹配支持键盘操作；
- SVG 提供可读标题或等价文字描述；
- 当前选择同时使用边框、图标和文字状态，不只变色；
- 进度变化用 `aria-live` 克制播报；
- 焦点在页面切换后回到主标题；
- 颜色对比满足 WCAG AA 的正文要求。

## 8. 结果计算边界

前端使用统一的 `AssessmentTransport` 接口提交答案并接收服务端形状的评分结果，页面组件和任务数据始终不读取正确答案。

本轮提供两种适配器：

- `LocalPrototypeAdapter`：只用于本地演示和自动化测试；答案键放在独立的 `prototype` 模块中，并在代码和构建说明中标记“不可用于生产”；
- `ApiAssessmentAdapter`：正式环境接口；前端提交不透明答案 ID、呈现顺序和事件，后端返回评分点、质量标记和版本化报告数据。

为了让无后端的前端原型走通，本地适配器后还保留一个明确标记为 `prototype` 的证据聚合器：

- 根据任务评分点汇总到 15 个二级机制；
- 一级能力只有在多个机制和不同任务共同支持时才形成优势描述；
- 跨表征任务只作辅助观察，不单独决定优势；
- 速度不加分；
- 不采用未经实测的固定“高/中/低”阈值；
- 证据不清楚时降低文案确定性，不强行排出完整第一至第五名；
- 学科匹配使用版本化权重和任务标签，并在代码中标记为待校准配置。

这一适配器和聚合器用于界面联调，不代表正式测量算法。生产构建必须禁用本地答案模块；生产版由后端返回可追溯的报告数据，前端只负责渲染。

## 9. 错误和异常处理

- 无法写入本地存储：允许继续本次会话，但持续提示不要刷新；
- 题目定义无效：阻止进入该题，显示题目版本和可复制的错误编号；
- 图形资源加载失败：内联 SVG 不依赖网络；
- 页面切后台：暂停有效作答计时，返回后继续；
- 连续快速提交或无选择提交：由交互状态阻止；
- 旧版 25 题数据：不迁移为 30 题结果，提示重新开始；
- 报告计算失败：保留完整证据并提供重试，不让学生重新作答。

## 10. 测试与验收

### 10.1 自动化测试

- 四项信息必填和手机号校验；
- Deck A/B 正确插入流程，且不可返回复看；
- 恰好 30 个位置，每个一级能力 6 个、每个二级机制 2 个；
- 17 个直接任务、8 个跨表征任务、5 个换场景任务；
- 所有任务有唯一 ID、版本、评分点和可用交互；
- 位置 06 映射唯一解；
- 位置 08 SVG 正确答案唯一且无试拼预览；
- 未作答不可提交，提交后不显示对错；
- 进度不暴露固定题数；
- 刷新可以恢复，版本变化会拒绝混用旧数据；
- 英语学生不显示日语，日语学生不显示英语；
- 报告包含一句话结论、雷达图和五个模块；
- 报告不出现排名、百分位、能力等级、固定天赋或保证提分表述。

### 10.2 浏览器验收

至少检查：

- 390×844 手机视口；
- 360×800 较窄手机视口；
- 768px 平板视口；
- 1440px 桌面视口；
- 键盘完整走通；
- 刷新、切后台和恢复；
- iOS Safari 与 Chromium 核心路径。

视觉验收逐屏与四张既有设计基准对照，重点检查字体层级、留白、颜色、底部操作、图形可读性和报告长页面节奏。

## 11. 实施顺序

1. 锁定位置 06、08 的专项复核结果并更新 30 题总稿；
2. 建立 30 题结构化数据和运行时类型；
3. 重构流程状态、信息采集、记忆材料和进度恢复；
4. 实现共用任务框架及七类交互组件；
5. 接入全部 30 个任务，逐题做答案和手机交互核验；
6. 实现原型证据聚合、学科任务映射和五段式报告；
7. 补齐单元测试和完整流程测试；
8. 在四类视口逐屏做视觉验收并修正；
9. 构建生产包，输出本地运行说明和剩余校准边界。

## 12. 完成标准

只有同时满足以下条件才视为本轮前端完成：

- 学生可在手机上从信息采集连续完成到报告；
- 30 个任务均来自最新版总稿，06、08 为复核后的新版本；
- 页面不再出现旧版 10 分钟、25 题、选科组合或“入口类型”逻辑；
- 全流程刷新可恢复，没有答案泄漏和即时对错；
- 报告结构、学科顺序和学习建议符合蓝图；
- 自动化测试、类型检查和生产构建全部通过；
- 关键页面与既有视觉基准一致；
- 代码清楚标出原型计算与正式校准算法的边界。
